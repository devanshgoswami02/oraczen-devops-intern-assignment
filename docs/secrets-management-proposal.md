# Secrets Management Proposal (Part 5 — Stretch)

## Current state

The PostgreSQL password is auto-generated by the Bitnami PostgreSQL
subchart and stored as a Kubernetes Secret.

The application reads the password through `secretKeyRef`. No plaintext
database password is stored in `values-prod.yaml`.

However, Kubernetes Secrets are base64-encoded rather than automatically
providing encryption at rest. Their security therefore also depends on
the Kubernetes/etcd security configuration.

## Recommendation: External Secrets Operator + AWS Secrets Manager

For a production AWS EKS environment, I would use External Secrets
Operator (ESO) together with AWS Secrets Manager.

### Comparison

**Sealed Secrets**

Sealed Secrets encrypts Kubernetes Secret data so an encrypted resource
can safely be stored in Git. However, the original secret still needs a
source of truth outside Git.

**SOPS**

SOPS can encrypt sensitive values in Git and works well with GitOps.
However, it also requires a separate key-management/source-of-truth
strategy.

**External Secrets Operator**

ESO allows the actual secret to remain in AWS Secrets Manager. Kubernetes
receives a Secret generated and continuously synchronized by ESO.

This provides a better separation between application configuration in
Git and sensitive credentials stored in a dedicated secrets system.

AWS Secrets Manager also provides access control, auditing, and secret
rotation capabilities.
